1.3 LAYER-BY-LAYER FOLDER RESPONSIBILITIES
--------------------------------------------------------------------------------
1. Presentation Layer ('frontend/src/'):
   - Responsible for user experience, data visualization, and accessibility.
   - Built with React 19, Vite, Tailwind CSS, Lucide icons, and Recharts.
   - Communicates with the backend strictly through strongly-typed Axios API clients.
   - Stores authentication state in React Context and persists tokens in localStorage.

2. Application & Orchestration Layer ('backend/app/api/' & 'backend/app/services/'):
   - FastAPI modular controllers handle request validation via Pydantic v2 schemas.
   - Dependency injection provides database sessions and authenticated user context.
   - Service classes encapsulate transactions, domain rules, state machines, and RBAC.

3. Persistence & Relational Layer ('backend/app/models/' & 'database/'):
   - Contains 23 SQLAlchemy 2.x declarative models representing the normalized schema.
   - PostgreSQL 17 provides ACID compliance, foreign key integrity, and relational views.
   - Alembic manages schema versioning and schema migrations.

4. Machine Learning & Predictive Layer ('ml/'):
   - Contains serialized production artifacts: preprocessor pipeline and calibrated model.
   - 'predictor.py' exposes a clean Python API for batch and single-task delay estimation.
   - Rejects unauthorized task or employee identifiers to prevent predictive bias.

5. Generative AI & Copilot Layer ('backend/app/core/llm_provider.py' & 'copilot_tools.py'):
   - Implements multi-turn tool-calling loop (OpenAI-compatible / Gemini-compatible).
   - Enforces strict database grounding through 10 read-only operational tools.
   - Features an automated deterministic engine fallback for offline resilience.

2.1 BUSINESS OBJECTIVE & MISSION
--------------------------------------------------------------------------------
HR Flow is an enterprise operational management and action intelligence platform
specifically built for technology organizations. It resolves the operational
chaos typical of distributed HR teams by centralizing employee lifecycle milestones,
tracking service-level agreements (SLAs), forecasting task delay risks through
calibrated machine learning, and offering a database-grounded AI copilot to
assist HR professionals with their day-to-day workload.

2.2 THE OPERATIONAL PROBLEM STATEMENT
--------------------------------------------------------------------------------
Modern human resources management involves dozens of concurrent, inter-dependent
workflows:
- Onboarding requires laptop provisioning, background checks, and orientation.
- Probation mandates timely reviews between employees and reporting managers.
- Confirmation requires formal manager recommendations and HR approval.
- Compliance requires document collection, verification, and audit readiness.
- Performance management involves periodic review cycles and touchpoints.
- Offboarding demands strict asset recovery, clearances, and handover tracking.

In traditional environments, these workflows become fragmented across spreadsheets,
email threads, and standalone ticketing tools. This leads to:
1. Operational Blindspots: Overdue tasks go unnoticed until SLAs are breached.
2. Missed Milestones: Probation periods lapse without formal evaluation.
3. Compliance Risks: Missing or unverified documents create regulatory exposure.
4. Reactive Decision Making: HR managers cannot identify bottlenecks in advance.

HR Flow solves this problem by consolidating all operational tasks into an
action-oriented dashboard, enforcing lifecycle state machines, automatically
routing follow-ups and escalations, and providing statistical delay risk warnings.

2.3 TARGET USER PERSONAS & ROLE MATRIX
--------------------------------------------------------------------------------
The system supports four distinct operational roles with tailored permissions:

1. HR Administrator (Role Code: 'ADMIN'):
   - Scope: Enterprise-wide (all departments, employees, tasks, and system settings).
   - Responsibilities: User provisioning, role assignment, system health monitoring,
     lifecycle template management, and configuration.

2. HR Manager (Role Code: 'HR_MANAGER'):
   - Scope: Enterprise-wide operational oversight.
   - Responsibilities: Monitoring SLAs, approving confirmations, resolving Level 2/3
     escalations, reviewing bottlenecks, and tracking company-wide KPIs.

3. HR Operations Specialist / HR Executive (Role Code: 'HR_EXECUTIVE'):
   - Scope: Assigned operational responsibilities and operational tasks.
   - Responsibilities: Creating tasks, verifying compliance documents, conducting
     onboarding checklists, initiating follow-ups, and resolving Level 1 escalations.

4. Reporting Manager / People Manager (Role Code: 'REPORTING_MANAGER'):
   - Scope: Strictly scoped to their direct and indirect subordinate employees.
   - Responsibilities: Submitting probation feedback, approving team task completions,
     recommending confirmations, and reviewing team milestones.

2.4 CORE FEATURE SUITE
--------------------------------------------------------------------------------
1. Executive HR Overview Dashboard:
   - Real-time KPI summary (Total Employees, Joiners, Exits, Open & Overdue Tasks).
   - Six-stage lifecycle pipeline visualization.
   - Multi-category 'Attention Required' triage table.
   - Upcoming lifecycle milestone schedule.
   - AI-powered Daily Operational Briefing.

2. 6-Stage Employee Lifecycle Management:
   - Onboarding, Probation, Confirmation, Documentation, Performance, Offboarding.
   - Reusable workflow templates with automated task fan-out.
   - Visual lifecycle calendar with date-filtered event tracking.

3. Operational Action Center & Task Management:
   - 'My Tasks' (personalized work queue) and 'Team Tasks' (hierarchical view).
   - Task dependencies (blocking/prerequisite task chains).
   - SLA tracking, deadline extensions, reassignment, and audit history.

4. Follow-Ups, Touchpoints & Escalation Engine:
   - Distinct touchpoint tracking for items awaiting third-party response.
   - Automated daily SLA scanner triggering reminders for approaching deadlines.
   - Three-level escalation hierarchy with formal acknowledgment and resolution.

5. Machine Learning Task Delay Risk Prediction:
   - Calibrated probabilistic classifier forecasting task delay probability.
   - Real-time explainability factors highlighting primary drivers of risk.
   - Identification of systemic bottlenecks (blockers, backlog, stalled items).

6. HR Operations Copilot (GenAI Assistant):
   - Conversational assistant embedded directly in the workspace.
   - 10 database-grounded operational tools ensuring zero hallucinations.
   - Automatic deterministic fallback engine when external LLMs are offline.
   - Role-scoped data boundaries preventing managers from accessing unauthorized data.

2.5 TECHNOLOGY STACK BREAKDOWN
--------------------------------------------------------------------------------
- Frontend Framework: React 19 (TypeScript, Vite build tool)
- Styling & Components: Tailwind CSS, shadcn/ui component primitives, Lucide React
- Charting & Visualization: Recharts (responsive vector charts)
- HTTP Client: Axios with interceptors, bearer auth injection, and error normalization
- Backend Framework: Python 3.12+, FastAPI (ASGI asynchronous framework)
- Database ORM: SQLAlchemy 2.0 (Modern mapped_column typing, Session pooling)
- Database Migrations: Alembic
- Database Engine: PostgreSQL 17 on localhost:5432 (Database: hr_operations_db)
- Machine Learning: Scikit-learn (CalibratedClassifierCV, Pipeline), Pandas, NumPy
- GenAI & LLM Integration: OpenAI-compatible REST integration / Google Gemini API
- Testing Frameworks: Pytest (Backend) and Vitest + React Testing Library (Frontend)

2.6 HIGH-LEVEL OPERATIONAL ARCHITECTURE
--------------------------------------------------------------------------------
HR Flow operates as a layered Modular Monolith. The React Single Page Application
(SPA) communicates with the FastAPI backend over REST. The backend validates
incoming requests, enforces RBAC, executes domain logic, queries PostgreSQL,
evaluates ML models, and interfaces with the LLM provider when copilot inquiries
are received.

PART 3 — COMPLETE SYSTEM ARCHITECTURE

3.1 FRONTEND ARCHITECTURAL DESIGN
--------------------------------------------------------------------------------
The frontend is designed around modular feature slices and reactive state
management:

1. Entry Point ('src/main.tsx' & 'src/App.tsx'):
   - Initializes React root in strict mode.
   - Wraps the component tree in 'BrowserRouter' and 'AuthProvider'.

2. Routing Architecture ('src/routes/AppRoutes.tsx' & 'ProtectedRoute.tsx'):
   - Defines public routes ('/login', '/unauthorized', '/404').
   - Enforces authentication and role verification via 'ProtectedRoute'.
   - Unauthenticated users are redirected to '/login' while preserving the
     intended destination in navigation state.
   - Users attempting to access forbidden routes are routed to '/unauthorized'.

3. Application Shell ('src/layouts/AppLayout.tsx'):
   - Provides the standard responsive workspace layout.
   - Comprises a collapsible Sidebar navigation, a top Header with user profile
     information and notifications, and a scrollable main content area.

4. API Service Layer ('src/api/'):
   - Centralized Axios client ('axiosClient.ts') configured with a 15-second timeout,
     automatic bearer token injection from localStorage, and 401 response handling.
   - Encapsulates backend endpoints into domain services ('authApi', 'taskApi',
     'lifecycleApi', 'dashboardApi', 'mlIntelligenceApi', 'slaApi', etc.).

5. UI Component Library ('src/components/ui/'):
   - Atomic design primitives (Button, Input, Select, Badge, Card, Table, Modal,
     Alert, Pagination, Skeleton).

3.2 BACKEND MODULAR MONOLITH ARCHITECTURE
--------------------------------------------------------------------------------
The backend is structured into clear architectural tiers within a single deployable
service:

1. Application Lifecycle & Startup ('app/main.py'):
   - Configures FastAPI application instance, CORS middleware, and custom exception
     handlers.
   - Includes 'ensure_postgres_running()' pre-flight routine to automatically start
     the PostgreSQL Windows service if stopped, ensuring reliable boot sequences.
   - Spawns 'run_daily_sla_scheduler()' in the background to scan tasks for SLA breaches.

2. API Routing Tier ('app/api/v1/router.py'):
   - Consolidates 12 modular sub-routers under the '/api/v1' prefix.
   - Implements dependency injection for database sessions ('get_db') and user
     authentication ('get_current_user', 'require_active_user', 'require_role').

3. Domain Service Layer ('app/services/'):
   - Encapsulates all transactional business logic, domain invariant validation,
     and multi-model updates.
   - Controllers never execute raw database operations directly; they delegate
     exclusively to service classes.

4. Data Persistence Tier ('app/db/' & 'app/models/'):
   - 'session.py' configures SQLAlchemy engine with connection pooling (pool_size=10,
     max_overflow=20, pool_pre_ping=True).
   - 'base.py' defines the declarative base metadata.
   - 23 ORM models define explicit relationships, cascade behaviors, and indexes.

3.3 DATABASE DESIGN & ORM DATA ACCESS LAYER
--------------------------------------------------------------------------------
The relational database utilizes PostgreSQL 17. The design separates organizational
structure (Departments, Roles, Employees, Users) from operational workflows
(Tasks, Dependencies, FollowUps, Escalations) and lifecycle states (Onboarding,
Probation, Confirmation, Documentation, Performance, Offboarding).

All primary keys use BigInteger auto-incrementing identifiers. Foreign keys strictly
enforce referential integrity using 'ON DELETE RESTRICT' or 'ON DELETE CASCADE'
depending on data ownership.

3.4 EXTERNAL INTEGRATIONS & ADVISORY AI SUBSYSTEMS
--------------------------------------------------------------------------------
1. Machine Learning Inference Service ('ml/predictor.py'):
   - Scikit-learn Pipeline loaded from serialized joblib artifacts.
   - Evaluates task attributes in memory without external API dependencies.
   - Operates in 'shadow mode' to provide advisory risk signals to HR staff.

2. Generative AI Copilot ('app/core/llm_provider.py'):
   - Connects to OpenAI-compatible REST endpoints or Google Gemini APIs.
   - Employs a multi-turn function-calling loop with 10 database-grounded tools.
   - Includes a deterministic grounded engine that executes the same operational
     queries if external LLM credentials are not configured or if the network is down.

4.1 HR OVERVIEW DASHBOARD & EXECUTIVE INTELLIGENCE
--------------------------------------------------------------------------------
The HR Overview Dashboard serves as the command center for operational leaders,
HR managers, and team leads. It aggregates metrics across the entire employee
lifecycle, surfaces critical bottlenecks requiring immediate intervention, and
delivers an AI-synthesized daily briefing.

1. Greeting & Contextual Header:
   - Displays a dynamic greeting reflecting the current time of day in IST
     ("Good morning", "Good afternoon", "Good evening").
   - Presents a Department Filter dropdown allowing managers to isolate data for
     specific functional units (Engineering, Product, Marketing, Sales, HR, etc.).
   - Admins and HR Managers can filter across any department; Reporting Managers
     are constrained to their own team members.

2. KPI Cards & Mathematical Derivation:
   The dashboard displays four primary operational KPIs plus four supporting metrics.
   Each KPI is calculated in 'DashboardService.get_dashboard_overview()' using
   explicit SQL queries evaluated against current date in 'Asia/Kolkata' timezone:

   a) Total / Active Employees:
      - Definition: The total active headcount under management.
      - SQL Logic:
        SELECT COUNT(id) FROM employees
        WHERE employment_status IN ('ACTIVE', 'CONFIRMED')
          AND [Role-Scoping Filter];

   b) New Joiners This Month:
      - Definition: Headcount added in the current calendar month.
      - SQL Logic:
        SELECT COUNT(id) FROM employees
        WHERE EXTRACT(YEAR FROM date_of_joining) = today.year
          AND EXTRACT(MONTH FROM date_of_joining) = today.month
          AND [Role-Scoping Filter];

   c) Exits This Month:
      - Definition: Employees who completed offboarding in current calendar month.
      - SQL Logic:
        SELECT COUNT(o.id) FROM offboarding_records o
        JOIN employees e ON o.employee_id = e.id
        WHERE o.overall_status = 'COMPLETED'
          AND EXTRACT(YEAR FROM o.last_working_day) = today.year
          AND EXTRACT(MONTH FROM o.last_working_day) = today.month
          AND [Role-Scoping Filter];

   d) Pending HR Actions / Open Tasks:
      - Definition: Operational tasks currently requiring action or resolution.
      - SQL Logic:
        SELECT COUNT(t.id) FROM tasks t
        JOIN employees e ON t.employee_id = e.id
        WHERE t.status NOT IN ('COMPLETED', 'CANCELLED')
          AND [Role-Scoping Filter];

   e) Overdue Tasks:
      - Definition: Open tasks whose due date has passed.
      - SQL Logic:
        SELECT COUNT(t.id) FROM tasks t
        JOIN employees e ON t.employee_id = e.id
        WHERE t.due_date < today
          AND t.status NOT IN ('COMPLETED', 'CANCELLED')
          AND [Role-Scoping Filter];

   f) Tasks Due in Next 7 Days:
      - Definition: Approaching deadlines strictly within the next 7 days.
      - SQL Logic:
        SELECT COUNT(t.id) FROM tasks t
        JOIN employees e ON t.employee_id = e.id
        WHERE t.due_date >= today
          AND t.due_date <= today + INTERVAL '7 days'
          AND t.status NOT IN ('COMPLETED', 'CANCELLED')
          AND [Role-Scoping Filter];

3. Six-Stage Lifecycle Pipeline:
   Visualizes the distribution of employees across all active lifecycle stages:
   - Onboarding: Count of 'onboarding_records' with 'overall_status = IN_PROGRESS'.
   - Probation: Count of 'probation_records' with 'status IN (UNDER_REVIEW, EXTENDED)'.
   - Confirmation: Count of 'confirmation_records' with 'status = PENDING_APPROVAL'.
   - Documentation: Count of 'employee_documents' with 'status IN (PENDING_SUBMISSION, SUBMITTED)'.
   - Performance Reviews: Count of 'performance_reviews' with 'status IN (DRAFT, IN_PROGRESS, SUBMITTED)'.
   - Offboarding: Count of 'offboarding_records' with 'overall_status = IN_PROGRESS'.

4. 'Attention Required' Triage Table:
   Presents a consolidated operational backlog prioritized across four categories:
   - Category A: Overdue Tasks (tasks past deadline, ordered by oldest due date).
   - Category B: Pending Confirmations (records awaiting manager or HR approval
     where target date is within 14 days).
   - Category C: Open Escalations (escalation records in 'OPEN' or 'PENDING' status).
   - Category D: High Risk Tasks (tasks evaluated by the ML model with delay
     probability >= 0.70).
   Each row provides deep-links to directly open the Action Center or Lifecycle tab.

5. Upcoming Milestones Schedule:
   Tracks employee touchpoints over the next 30 days:
   - Day 1, Day 7, Day 30, Day 60, Day 90 Onboarding milestones.
   - Probation review deadlines.
   - Confirmation due dates.
   - Employee Last Working Days (Offboarding).

6. AI-Powered Daily Operational Briefing:
   - Serves as the executive summary of the day's operational priorities.
   - Process Flow:
     1. 'DashboardService' or 'CopilotService' calls 'tool_get_hr_daily_briefing_context'.
     2. Collects verified facts: counts of overdue tasks, probation reviews due,
        pending confirmations, pending follow-ups, open escalations, and active joiners.
     3. If an LLM API key is configured, formats a strict system prompt containing
        the facts and prompts the model to generate a concise, professional executive
        summary.
     4. If the LLM is unconfigured, offline, or times out, the system automatically
        invokes the Deterministic Briefing Engine:
        "Good morning! Currently managing {active_employees} active employees across
        6 lifecycle stages with {open_tasks} total open operational tasks. There are
        {overdue_tasks} overdue tasks and {pending_followups} pending follow-ups
        requiring attention today."
     5. Attaches structured 'key_updates' cards with severity tags ('HIGH', 'MEDIUM',
        'INFO') and clickable direct-action navigation routes.

4.2 EMPLOYEE LIFECYCLE MANAGEMENT (6 CORE STAGES)
--------------------------------------------------------------------------------
The Employee Lifecycle module manages all transitions from hiring to separation.
It is accessed via '/lifecycle' with dedicated tabbed views and template engines.

1. Onboarding Stage ('OnboardingTab.tsx'):
   - Tracks incoming joiners from pre-boarding through their first 90 days.
   - Database Model: 'OnboardingRecord' linked to 'Employee'.
   - Milestones: Day 1 (Welcome & IT Setup), Day 7 (Team Immersion), Day 30 (Check-in),
     Day 60 (Mid-probation Check), Day 90 (Onboarding Completion).
   - Statuses: 'PRE_BOARDING', 'IN_PROGRESS', 'COMPLETED', 'DELAYED'.
   - Checklist & Task Fan-out: When an onboarding template is executed, tasks are
     automatically spawned in the 'tasks' table for IT hardware provisioning,
     HR orientation, benefits enrollment, and security access.

2. Probation Stage ('ProbationTab.tsx'):
   - Monitors the 90-to-180 day statutory and policy probation periods.
   - Database Model: 'ProbationRecord'.
   - Fields: 'probation_start_date', 'probation_end_date', 'review_due_date',
     'evaluation_status', 'feedback_submission_date'.
   - Statuses: 'UNDER_REVIEW', 'CONFIRMED', 'EXTENDED', 'FAILED'.
   - Workflow: When a probation review date approaches (within 14 days), an automated
     reminder task is assigned to the employee's Reporting Manager to submit feedback.

3. Confirmation Stage ('ConfirmationTab.tsx'):
   - Formal transition from probationary employee to confirmed permanent staff.
   - Database Model: 'ConfirmationRecord'.
   - Two-Step Approval Workflow:
     Step 1: Reporting Manager submits recommendation ('RECOMMEND_CONFIRMATION',
     'RECOMMEND_EXTENSION', 'RECOMMEND_SEPARATION') via 'POST /api/v1/lifecycle/confirmation/{id}/recommend'.
     Step 2: HR Manager or Admin approves or rejects the recommendation via
     'POST /api/v1/lifecycle/confirmation/{id}/approve'.
   - Upon confirmation approval, the employee's 'employment_status' in the 'employees'
     table is automatically updated from 'ACTIVE' (Probation) to 'CONFIRMED'.

4. Documentation & Compliance Stage ('DocumentationTab.tsx'):
   - Enforces statutory document verification (ID proof, education certificates,
     relieving letters, NDA, PAN/Tax records).
   - Database Models: 'DocumentRequirement' (catalog) and 'EmployeeDocument' (submissions).
   - Verification Workflow:
     HR Executives review submitted documents and verify them via
     'POST /api/v1/lifecycle/documents/{id}/verify'.
   - Verification updates status to 'VERIFIED', records the verifying user ID,
     and records the verification timestamp.

5. Performance Reviews Stage ('PerformanceTab.tsx'):
   - Manages annual, half-yearly, or quarterly appraisal cycles.
   - Database Model: 'PerformanceReview'.
   - Fields: 'review_cycle_name', 'reviewer_id', 'employee_id', 'rating',
     'manager_comments', 'self_assessment', 'status'.
   - Statuses: 'DRAFT', 'SUBMITTED', 'IN_REVIEW', 'COMPLETED'.
   - Enables HR Admins to create new cycles and bulk-assign reviews to managers.

6. Offboarding & Exit Stage ('OffboardingTab.tsx'):
   - Orchestrates voluntary resignations and company-initiated separations.
   - Database Model: 'OffboardingRecord'.
   - Fields: 'resignation_date', 'last_working_day', 'exit_interview_status',
     'kt_status' (Knowledge Transfer), 'it_clearance_status', 'finance_clearance_status',
     'overall_status'.
   - Automated Clearances: Tasks are assigned to IT (revoke credentials, recover
     hardware), Finance (full & final settlement calculation), and Department Leads
     (handover review).
   - Completion: When all clearances are verified, the HR Specialist completes the
     record via 'POST /api/v1/lifecycle/offboarding/{id}/complete', updating the
     employee's 'employment_status' to 'INACTIVE'.

7. Reusable Lifecycle Templates ('TemplatesTab.tsx'):
   - Enables HR Admins to configure multi-task templates for repeatable processes.
   - Database Model: 'TaskTemplate'.
   - Execution Engine: 'LifecycleService.execute_templates()' fans out templates
     into live instances in the 'tasks' table with calculated relative due dates
     (e.g., 'date_of_joining + 3 days').

8. Lifecycle Calendar ('CalendarTab.tsx'):
   - Aggregates all milestones, task deadlines, and review dates into a unified
     monthly/weekly operational schedule.

4.3 TASK MANAGEMENT & OPERATIONAL ACTION CENTER
--------------------------------------------------------------------------------
Accessed via '/action-center' or '/tasks', this module manages operational work
queues with deep filtering, dependency management, and SLA tracking.

1. Work Queues:
   - 'My Tasks': Strictly displays tasks where the authenticated user is the assigned
     owner ('Task.owner_id == current_user.id').
   - 'Team Tasks': For Reporting Managers, displays tasks belonging to any of their
     subordinates in the reporting hierarchy. For HR Managers and Admins, displays
     all company tasks.
   - 'All Tasks': Unrestricted view available to Admins and HR Managers.

2. User vs. Employee Identity Distinction:
   - 'assigned_to_user_id' / 'owner_id': The authenticated user account responsible
     for executing the operational task (e.g., an IT Admin or HR Specialist).
   - 'employee_id': The subject employee whom the task concerns (e.g., the new joiner
     receiving a laptop).
   - 'created_by_user_id': The user who initiated the task.

3. Task Attributes:
   - 'task_code': Unique business key (e.g., 'TSK-03268').
   - 'priority': 'CRITICAL', 'HIGH', 'MEDIUM', 'LOW'.
   - 'status': 'PENDING', 'IN_PROGRESS', 'BLOCKED', 'DELAYED', 'COMPLETED', 'CANCELLED'.
   - 'lifecycle_category': 'ONBOARDING', 'PROBATION', 'CONFIRMATION', 'COMPLIANCE',
     'PERFORMANCE', 'OFFBOARDING', 'GENERAL'.
   - 'due_date': Strict calendar date for SLA completion.

4. Task Dependencies & Blockers:
   - Database Model: 'TaskDependency' ('task_id', 'prerequisite_task_id').
   - Invariant: A task with incomplete prerequisite dependencies cannot be marked
     'COMPLETED'. Attempting to do so raises an 'AppException' (HTTP 400).
   - When a prerequisite task is completed, dependent tasks transition from
     'BLOCKED' to 'IN_PROGRESS' or 'PENDING'.

5. Reassignment & Deadline Extension:
   - Reassignment: 'POST /api/v1/tasks/{id}/reassign' changes the assigned owner and
     records an audit trail entry in 'task_status_history'.
   - Deadline Extension: 'POST /api/v1/tasks/{id}/extend-deadline' updates 'due_date',
     increments 'deadline_extension_count', and records the extension reason.

6. Task Completion & Lifecycle Synchronization:
   - When a task is marked 'COMPLETED', 'TaskService._sync_lifecycle_on_completion()'
     checks whether this task is the final step in an onboarding checklist,
     document submission, or clearance activity.
   - If all sibling tasks in that lifecycle stage are completed, the parent lifecycle
     record status automatically updates to 'COMPLETED'.

4.4 FOLLOW-UPS, REMINDERS & MULTI-TIER ESCALATIONS
--------------------------------------------------------------------------------
Accessed via '/follow-ups', this module manages touchpoints where HR is awaiting
an external or internal stakeholder response, preventing tasks from slipping.

1. Tasks vs. Follow-Ups:
   - A 'Task' is an internal work unit owned by an operator (e.g., "Draft employment contract").
   - A 'Follow-Up' is a tracked touchpoint awaiting response from an external party
     (e.g., "Waiting for employee to return signed NDA" or "Waiting for manager feedback").
   - Follow-Ups prevent operators from closing tasks prematurely while waiting for replies.

2. Follow-Up Lifecycle:
   - Model: 'FollowUp' ('task_id', 'employee_id', 'initiator_user_id', 'target_user_id',
     'next_follow_up_date', 'response_received', 'notes').
   - Statuses: 'AWAITING_RESPONSE', 'RESPONSE_RECEIVED', 'OVERDUE', 'RESOLVED'.
   - Acknowledgment: When the stakeholder responds, HR logs the note via
     'POST /api/v1/follow-ups/{id}/acknowledge', setting 'response_received = True'.

3. Automated SLA Reminders:
   - Background worker 'run_daily_sla_scheduler()' in 'app/main.py' runs every 24 hours.
   - It identifies tasks due within 48 hours or already overdue without recent touchpoints.
   - Generates notifications in the 'notifications' table and increments 'reminder_count'.

4. Multi-Tier Escalations:
   - Model: 'Escalation' ('task_id', 'employee_id', 'level', 'reason', 'status').
   - Three Escalation Levels:
     Level 1: Operational Warning (assigned to HR Executive or Direct Manager).
     Level 2: Management Escalation (assigned to HR Manager).
     Level 3: Executive Intervention (assigned to Head of HR / Admin).
   - Resolution Workflow:
     Resolving an escalation ('POST /api/v1/escalations/{id}/resolve') records
     resolution notes and marks the escalation 'RESOLVED'.
     Crucial distinction: Resolving an escalation acknowledges and addresses the
     operational delay, but does NOT automatically complete the underlying task.
     The task itself must still be executed to completion.

4.5 ML INTELLIGENCE & TASK DELAY RISK ENGINE
--------------------------------------------------------------------------------
Accessed via '/ml-intelligence', this module provides predictive risk signals
and structural bottleneck analysis.

1. Machine Learning Problem Statement:
   - Predicts whether an active HR operational task will breach its SLA deadline
     ('is_delayed' = True/False) before completion.
   - Allows HR managers to intervene proactively rather than reacting after a breach.

2. Dataset & Training Provenance:
   - Source: Standardized operational dataset in 'datasets/ml_ready/' and 'ml/datasets/'.
   - Spans 24 months of synthetic organizational operations (360 employees, 65,000+ rows).
   - Features 8 approved, domain-validated predictors:
     1. 'days_remaining': Calendar days from current date to task due_date.
     2. 'task_category': ONBOARDING, PROBATION, CONFIRMATION, COMPLIANCE, OFFBOARDING.
     3. 'task_priority': CRITICAL, HIGH, MEDIUM, LOW.
     4. 'current_status': IN_PROGRESS, PENDING, BLOCKED.
     5. 'reminder_count': Number of automated/manual reminders already sent.
     6. 'owner_previous_delay_rate': Historical SLA breach rate of the assigned owner.
     7. 'owner_current_workload': Total open tasks currently assigned to the owner.
     8. 'dependency_status': NONE, ALL_MET, PENDING.

3. Strict Anti-Leakage & Bias Safeguards:
   - 'predictor.py' enforces an explicit blacklist ('UNAUTHORIZED_FEATURES').
   - Any input containing 'id', 'task_id', 'employee_id', 'owner_id', 'department_id',
     or completion timestamps is rejected with a ValueError.
   - Protects the model from individual employee or operator bias.

4. Model Architecture & Calibration:
   - Scikit-learn Pipeline with StandardScaler for numeric features and
     OneHotEncoder for categorical features.
   - Base Classifier: Gradient Boosted Trees / Random Forest.
   - Calibration: Wrapped in 'CalibratedClassifierCV(method="sigmoid", cv=5)' to
     ensure output probabilities reflect true empirical risk.
   - Serialized Artifacts in 'ml/artifacts/phase_7a/':
     'preprocessor.joblib', 'calibrated_model.joblib', 'feature_schema.json',
     'model_metadata.json'.

5. Risk Thresholds & Tier Assignment:
   - Low Risk: Probability < 0.12 (Green badge: On track).
   - Medium Risk: Probability 0.12 to 0.22 (Yellow badge: Monitor closely).
   - High Risk: Probability >= 0.22 (Red badge: Urgent intervention recommended).

6. Operational Bottlenecks vs. ML Predictions:
   The UI clearly separates facts from statistical estimates:
   - ML Predictions: Advisory probability estimates of potential delay.
   - Operational Bottlenecks: Real-time deterministic facts queried from PostgreSQL:
     * Awaiting Responses (Follow-ups pending > 3 days).
     * Prerequisite Blockers (Tasks blocked by unresolved dependency chains).
     * Workload Backlog (Owners assigned > 12 active tasks).
     * Stalled Progress (In-progress tasks with no activity in 14 days).

7. Missing Model & Fallback Handling:
   - If model artifacts are missing or unreadable, 'MLIntelligenceService' catches
     the exception, logs a warning, and falls back to a deterministic heuristic
     based on 'days_remaining <= 2' and 'reminder_count >= 2'. The system never crashes.

4.6 HR OPERATIONS COPILOT & GENAI FUNCTION-CALLING ENGINE
--------------------------------------------------------------------------------
Accessed via '/ai-intelligence' or the embedded Copilot drawer, this module provides
a database-grounded conversational assistant for HR operators.

1. Architectural Design & Grounding Strategy:
   - LLM Provider: OpenAI-compatible REST API or Google Gemini API via 'LLMProvider'.
   - Grounding Policy: The LLM is strictly prohibited from answering factual questions
     from its internal parametric weights. It must retrieve live database records
     using approved tools.
   - Tool-Calling Loop:
     1. User submits query (e.g., "Which probation reviews are overdue?").
     2. 'LLMProvider' constructs a system prompt with strict hallucination boundaries
        and formats the query along with conversation history.
     3. Calls the LLM passing 10 registered function definitions ('TOOL_DEFINITIONS').
     4. LLM emits a 'tool_call' request with structured JSON arguments.
     5. Backend executes the requested tool in 'copilot_tools.py', injecting the
        active SQLAlchemy session and authenticated 'current_user'.
     6. Returns the tool execution result JSON to the LLM.
     7. LLM synthesizes a concise, professional answer and generates record citations.
     8. Loop runs up to 'settings.LLM_MAX_TOOL_ROUNDS' (default 4 rounds).

2. Complete Catalog of 10 Approved Grounded Tools:

   Tool 1: 'get_my_tasks'
   - Purpose: Retrieves tasks assigned to or owned by the authenticated HR user.
   - Arguments: status, due_date_range, priority, lifecycle_category, limit.
   - Returns: List of task summaries with status, due date, employee, and priority.
   - Security: Scoped to 'current_user.id'.

   Tool 2: 'search_hr_tasks'
   - Purpose: Searches operational tasks across the organization or team.
   - Arguments: query, status, priority, due_date_range, lifecycle_category, employee_id, limit.
   - Returns: Matching tasks with full metadata.
   - Security: Automatically filters to subordinate employees if caller is a Reporting Manager.

   Tool 3: 'get_lifecycle_activities'
   - Purpose: Retrieves lifecycle records across all 6 stages.
   - Arguments: process (ONBOARDING, PROBATION, CONFIRMATION, etc.), status, employee_id,
     due_date_range, is_overdue, limit.
   - Returns: Structured lifecycle records with progress percentages and milestone dates.

   Tool 4: 'get_followups'
   - Purpose: Retrieves pending touchpoints awaiting response or touchpoint date.
   - Arguments: status, employee_id, task_id, limit.
   - Returns: Follow-up records, target stakeholders, and next follow-up dates.

   Tool 5: 'get_escalations'
   - Purpose: Retrieves unresolved Level 1, 2, or 3 escalations.
   - Arguments: status, employee_id, level, limit.
   - Returns: Escalation records with assigned managers and breach reasons.

   Tool 6: 'get_operational_bottlenecks'
   - Purpose: Returns systemic workflow blockers (Awaiting Responses, Prerequisite
     Blockers, Workload Backlog, Stalled Items).
   - Arguments: category.
   - Returns: Categorized bottleneck counts and specific affected task codes.

   Tool 7: 'get_employee_hr_summary'
   - Purpose: Retrieves non-sensitive operational overview for a specific employee.
   - Arguments: employee_id_or_code, employee_name.
   - Returns: Current lifecycle stage, pending tasks, overdue count, and blockers.
   - Privacy: Strictly excludes salary, bank accounts, and personal identifiers.

   Tool 8: 'get_task_delay_assessment'
   - Purpose: Evaluates why a specific task is delayed or at risk.
   - Arguments: task_id_or_code.
   - Returns: Task status, days remaining, dependency blockers, and advisory ML
     delay probability.

   Tool 9: 'get_hr_daily_briefing_context'
   - Purpose: Gathers aggregated facts for generating the daily operational briefing.
   - Arguments: department_id.
   - Returns: Consolidated counts of overdue tasks, due reviews, and pending actions.

   Tool 10: 'draft_followup_message'
   - Purpose: Drafts a polite, formal, or urgent follow-up message for HR to review.
   - Arguments: task_id_or_code, followup_id, recipient_role, tone.
   - Returns: Formatted draft text.
   - Safety: Does NOT send emails or update records. Read-only drafting assistance.

3. Hallucination Prevention & Prompt Injection Defense:
   - Grounding: If a tool returns no matching records, the system prompt instructs the
     model to state: "I couldn't find any matching records in the HR Flow database."
   - Prompt Injection Defense: Database notes and comments are treated as untrusted data.
     The system prompt explicitly commands the model to ignore any instructions inside
     database strings that attempt to override system rules or reveal secret keys.
   - Read-Only Execution: The Copilot has ZERO write tools. It cannot independently
     reassign tasks, delete records, approve confirmations, or send emails.

4. Deterministic Grounded Engine (Offline Fallback):
   - If 'LLM_API_KEY' is missing, empty, or if network connectivity to OpenAI/Gemini fails,
     'LLMProvider._run_deterministic_grounded_engine()' executes.
   - It performs natural language keyword matching against the query, calls the exact
     same 10 database tools directly, formats a clean tabular response, and attaches
     verified record citations.
   - Ensures the application remains 100% operational in air-gapped or offline environments.

PART 5 — COMPLETE END-TO-END DATA FLOW TRACES (15 CORE WORKFLOWS)
================================================================================

This section traces information flow from the physical user action through the
frontend UI, HTTP transport, backend endpoint, authorization guards, business
services, relational SQL transactions, and back to the updated UI view.

--------------------------------------------------------------------------------
5.1 WORKFLOW 1: AUTHENTICATION & SESSION INITIALIZATION
--------------------------------------------------------------------------------
1. User Action: User enters work email (e.g. 'neha.saxena@auratech.in') and password
   ('Password@123') on 'LoginPage.tsx' and clicks "Sign In".
2. Frontend Component: 'LoginPage.handleSubmit()' validates email format and dispatches
   'login({ email, password })' through 'AuthContext'.
3. API Client: 'authApi.login()' issues 'POST /api/v1/auth/login' via 'axiosClient'.
4. Backend Endpoint: 'app.api.v1.endpoints.auth.login()' receives 'LoginRequest' schema.
5. Service Execution: 'AuthService.login(db, login_data)':
   - Queries 'users' table joined with 'roles' and 'employees':
     SELECT * FROM users WHERE email = 'neha.saxena@auratech.in';
   - Checks 'bcrypt.checkpw(password, user.hashed_password)'.
   - Verifies 'user.is_active == True'.
   - Updates 'user.last_login_at = datetime.now(timezone.utc)'.
   - Generates JWT bearer access token signed with 'settings.JWT_SECRET_KEY' (HS256)
     containing claims: 'sub', 'role', 'email', 'user_id', 'employee_id', 'exp'.
   - Returns 'TokenResponse'.
6. Frontend State Update:
   - 'AuthContext' stores 'access_token' in browser 'localStorage'.
   - Sets user state with profile and role metadata.
   - Axios interceptor attaches 'Authorization: Bearer <token>' to all subsequent calls.
   - React Router redirects user to '/dashboard'.

--------------------------------------------------------------------------------
5.2 WORKFLOW 2: TASK CREATION & ASSIGNMENT PROPAGATION
--------------------------------------------------------------------------------
1. User Action: HR Specialist opens Action Center, clicks "+ New Task", fills in
   title, category ('ONBOARDING'), priority ('HIGH'), due date, subject employee,
   and assigned owner, then clicks "Create Task".
2. Frontend Component: 'ActionCenterPage' submits form to 'taskApi.createTask()'.
3. API Transport: 'POST /api/v1/tasks' carrying 'TaskCreate' payload.
4. Authorization Guard: 'require_active_user' verifies valid JWT. If caller is a
   Reporting Manager, 'verify_reporting_manager_scope()' verifies that subject
   employee is in their reporting tree.
5. Service Execution: 'TaskService.create_task(db, current_user, data)':
   - Generates unique business code 'TSK-{random_int}'.
   - Inserts new row into 'tasks' table with 'status = PENDING'.
   - Inserts audit record into 'task_status_history' ('old_status = None', 'new_status = PENDING').
   - If prerequisite task IDs are provided, inserts rows into 'task_dependencies'.
   - Commits database transaction.
6. Frontend Refresh:
   - API returns 'TaskDetail' DTO.
   - Modal closes, React state re-fetches task lists, and newly created task appears
     at the top of the table.

--------------------------------------------------------------------------------
5.3 WORKFLOW 3: MY TASKS VIEW & ROLE-BASED FILTRATION
--------------------------------------------------------------------------------
1. User Action: User navigates to Action Center and clicks the "My Tasks" tab.
2. Frontend Component: 'ActionCenterPage' calls 'taskApi.getTasks({ filter: "my_tasks" })'.
3. API Transport: 'GET /api/v1/tasks?assigned_to_user_id={current_user.id}'.
4. Backend Controller: 'tasks.list_tasks()' calls 'TaskService.list_tasks()'.
5. Database Query:
   SELECT t.*, e.first_name, e.last_name, d.department_name
   FROM tasks t
   JOIN employees e ON t.employee_id = e.id
   LEFT JOIN departments d ON e.department_id = d.id
   WHERE t.owner_id = :current_user_id
   ORDER BY t.due_date ASC;

3. API Transport: 'GET /api/v1/tasks?scope=team'.
4. Authorization Logic:
   - Backend extracts 'current_user.employee_id'.
   - Calls 'get_reporting_employee_ids(db, manager_employee_id)'.
   - Executes recursive Common Table Expression (CTE) in PostgreSQL:
     WITH RECURSIVE subordinate_tree AS (
         SELECT id FROM employees WHERE reporting_manager_id = :manager_emp_id
         UNION ALL
         SELECT e.id FROM employees e
         JOIN subordinate_tree st ON e.reporting_manager_id = st.id
     )
     SELECT id FROM subordinate_tree;
5. Database Query:
   SELECT t.* FROM tasks t
   WHERE t.employee_id IN (:subordinate_ids)
   ORDER BY t.due_date ASC;

5.13 WORKFLOW 13: LIVE TASK DELAY RISK ASSESSMENT VIA MACHINE LEARNING
--------------------------------------------------------------------------------
1. User Action: User opens ML Intelligence tab or clicks "Inspect Risk" on a task card.
2. Frontend Component: 'MLIntelligencePage' calls 'mlIntelligenceApi.getTaskAssessment(taskId)'.
3. API Transport: 'GET /api/v1/ml-intelligence/tasks/{id}/assessment'.
4. Backend Service: 'MLIntelligenceService.get_task_assessment()':
   - Retrieves live task row from 'tasks' table.
   - Calculates 'days_remaining = task.due_date - today'.
   - Queries 'task_dependencies' to determine 'dependency_status'.
   - Queries owner history to calculate 'owner_previous_delay_rate' and 'owner_current_workload'.
   - Assembles 8-feature vector:
     [days_remaining, category, priority, status, reminder_count, delay_rate, workload, dependency]
   - Passes vector to 'TaskDelayRiskPredictor.predict_proba()'.
   - Calibrated classifier outputs delay probability: e.g. '0.78' (78% risk).
   - Maps probability to risk tier: 'HIGH'.
   - Computes local feature attribution: identifies that 'days_remaining = 1' and
     'owner_current_workload = 14' are the primary drivers of risk.
5. UI Render: Modal displays circular risk gauge (78% - High Risk) and lists top
   risk drivers with recommended mitigation steps.

- Connection Pool Settings ('app/db/session.py'):
  * 'pool_size = 10': Maintains up to 10 persistent connections in memory.
  * 'max_overflow = 20': Spawns up to 20 additional temporary connections under load.
  * 'pool_pre_ping = True': Issues a lightweight 'SELECT 1' test query prior to
    handing out a connection, discarding stale or severed database sockets.
  * 'autocommit = False', 'autoflush = False': Guarantees explicit transaction
    boundaries.
  * 'expire_on_commit = False': Retains loaded object attributes post-commit to
    prevent unnecessary lazy-load queries during DTO serialization.

7.4 USER IDENTITY VS. EMPLOYEE RECORD ARCHITECTURAL SEPARATION
--------------------------------------------------------------------------------
HR Flow implements a clean separation between human personnel and software users:
1. 'employees' represents the physical employee in the tech organization. It holds
   HR attributes: date of joining, salary grade, department, reporting manager,
   probation status, and last working day.
2. 'users' represents an authenticated software account with a password hash,
   email, role permissions, and active login state.
3. Decoupling Benefit: Not every employee has system access (e.g., external contractors
   or workers without desktop logins), and system accounts (e.g. system service bots)
   do not require an employee profile. When an employee is granted software access,
   'users.employee_id' holds a foreign key pointer to their employee record.

7.5 FOREIGN KEY CONSTRAINTS, CASCADES & INDEX OPTIMIZATION
--------------------------------------------------------------------------------
- 'ON DELETE RESTRICT': Applied to primary business associations (e.g., deleting a
  department that contains active employees is rejected by PostgreSQL; deleting an
  employee with active tasks is rejected).
- 'ON DELETE CASCADE': Applied to tightly-bound subordinate entities (e.g., deleting
  a task cascades to its 'task_dependencies' and 'task_status_history' rows).
- Critical Indexes:
  * 'idx_tasks_owner_status': B-Tree on (owner_id, status) for sub-millisecond My Tasks filtration.
  * 'idx_tasks_due_status': B-Tree on (due_date, status) for SLA and Overdue scanning.
  * 'idx_employees_reporting': B-Tree on (reporting_manager_id) for recursive tree traversal.
  * 'idx_users_email': Unique index on LOWER(email) for rapid login lookups.

9.4 HIERARCHICAL REPORTING SCOPE RESOLUTION ALGORITHM
--------------------------------------------------------------------------------
When a user with role 'REPORTING_MANAGER' accesses any endpoint, the backend does
not trust client-supplied employee IDs. Instead, it executes:
'get_reporting_employee_ids(db, current_user.employee_id)'

This function runs a recursive Common Table Expression (CTE) in PostgreSQL that
traverses the 'reporting_manager_id' foreign key relationship downwards through
all organizational tiers, returning a complete set of direct and indirect
subordinate employee IDs. All subsequent queries on tasks, lifecycle records,
reviews, and documents are automatically filtered with:
'WHERE employee_id IN (:subordinate_ids)'

9.5 DATA PRIVACY, GROUNDING PROTECTION & INJECTION DEFENSE
--------------------------------------------------------------------------------
1. PII Protection:
   - Sensitive financial and identity data (bank account numbers, salary amounts,
     tax identifiers) are strictly omitted from general API DTOs and are entirely
     inaccessible to the GenAI Copilot.
2. Read-Only AI Grounding:
   - The Copilot engine has no write tools. It cannot modify data, close tasks, or
     send emails autonomously.
3. Prompt Injection Defense:
   - System prompts explicitly instruct the LLM that database text fields (task notes,
     comments, descriptions) are untrusted third-party inputs. The model is commanded
     never to follow instructions embedded inside database records that attempt to
     bypass system rules.

PART 12 — CRITICAL BUSINESS RULES & STATUS LOGIC
================================================================================

12.1 TASK STATUS PROGRESSION & OVERDUE EVALUATION LOGIC
--------------------------------------------------------------------------------
1. Active vs. Terminal Tasks:
   - Active (Non-Terminal): 'PENDING', 'IN_PROGRESS', 'BLOCKED', 'DELAYED'.
     Counted towards workload backlog and pending action KPIs.
   - Terminal: 'COMPLETED', 'CANCELLED'. Excluded from backlog and SLA scanning.
2. Overdue Evaluation Rule:
   A task is mathematically OVERDUE if and only if:
   'due_date < current_date' AND 'status NOT IN ("COMPLETED", "CANCELLED")'.
   All dates are compared in the 'Asia/Kolkata' (IST) timezone.
3. Dependency Enforcement Rule:
   A task cannot transition to 'COMPLETED' if any prerequisite task in
   'task_dependencies' has a status other than 'COMPLETED'. The system raises an
   HTTP 400 'AppException' if an operator attempts premature completion.
4. Blocked Task Rule:
   A task with one or more pending prerequisite tasks is assigned status 'BLOCKED'.
   When the final prerequisite task is marked 'COMPLETED', the dependent task
   automatically transitions to 'IN_PROGRESS'.

12.2 LIFECYCLE STATE TRANSITIONS & MILESTONES
--------------------------------------------------------------------------------
1. Onboarding Progression:
   - 'PRE_BOARDING' -> 'IN_PROGRESS' -> 'COMPLETED'.
   - Trigger: 'onboarding_records.overall_status' transitions to 'COMPLETED' when
     all linked onboarding checklist tasks in 'tasks' are marked 'COMPLETED'.
2. Confirmation State Machine:
   - 'PENDING_EVALUATION' -> 'PENDING_APPROVAL' -> 'CONFIRMED' (or 'EXTENDED').
   - Reporting Manager recommendation transitions status to 'PENDING_APPROVAL'.
   - HR Approval transitions status to 'CONFIRMED' and automatically updates the
     employee's master 'employment_status' in 'employees' from 'ACTIVE' to 'CONFIRMED'.
3. Offboarding Clearances:
   - 'IN_PROGRESS' -> 'COMPLETED'.
   - Requires verification of: 'it_clearance_status = COMPLETED',
     'finance_clearance_status = COMPLETED', and 'kt_status = COMPLETED'.
   - Completion automatically transitions 'employees.employment_status' to 'INACTIVE'.

12.3 SLA REMINDER TRIGGERS & THRESHOLDS
--------------------------------------------------------------------------------
1. Automated Scanner Cadence:
   - 'run_daily_sla_scheduler()' runs in background every 24 hours.
2. Reminder Triggers:
   - Warning Reminder: Triggered when 'due_date <= today + 2 days' and no reminder
     was sent within the last 24 hours.
   - Breach Alert: Triggered when 'due_date < today' and task is still active.
3. Escalation Thresholds:
   - Level 1 Escalation: Spawned when a critical task is overdue by >= 2 days.
   - Level 2 Escalation: Spawned when a Level 1 escalation remains unacknowledged for >= 48 hours.
   - Level 3 Escalation: Spawned when a critical compliance or offboarding milestone
     is overdue by >= 5 days.

12.4 MACHINE LEARNING RISK TIER CLASSIFICATIONS
--------------------------------------------------------------------------------
- Output Probability: Calibrated float between 0.0000 and 1.0000.
- Risk Tiers:
  * Low Risk ('LOW'): Probability < 0.12 (Green indicator). Task is progressing normally.
  * Medium Risk ('MEDIUM'): 0.12 <= Probability < 0.22 (Yellow indicator). Approaching
    deadline or moderate workload backlog.
  * High Risk ('HIGH'): Probability >= 0.22 (Red indicator). Immediate operational
    intervention recommended.

13.1 ARCHITECTURAL ASSUMPTIONS
--------------------------------------------------------------------------------
1. Single Organization / Single Tenant:
   - The platform is engineered as an enterprise single-tenant modular monolith for

     not currently implemented.
2. Synchronous Database Operations:
   - The backend uses SQLAlchemy 2.0 synchronous session management with psycopg v3.
     While highly performant for this workload, high-concurrency microservice scaling
     would benefit from an asynchronous SQLAlchemy session factory.

13.2 MACHINE LEARNING SCOPE & BOUNDARY CONDITIONS
--------------------------------------------------------------------------------
1. Synthetic Training Ground:
   - The model was trained and calibrated on a 24-month synthetic organizational
     dataset (360 employees, 65,000+ relational rows). While statistically validated
     for internal consistency, retraining on production client data is necessary
     prior to live deployment.
2. Advisory Shadow Mode:
   - The ML model operates strictly in advisory 'shadow mode'. It provides early
     warning risk signals to human operators but cannot independently reassign,
     reschedule, or cancel tasks.

13.3 GENAI HALLUCINATION CONTAINMENT BOUNDARIES
--------------------------------------------------------------------------------
1. Read-Only Tool Execution:
   - The Copilot is structurally restricted to read-only tool execution. It cannot
     perform write mutations or send emails autonomously.
2. Token Window Context Bounds:
   - Session conversation history is bounded to the last 10 messages (5 user/assistant
     turns) to maintain fast inference times and prevent prompt context overflow.

14.3 TECHNICAL ARCHITECTURE DEFENSE
--------------------------------------------------------------------------------
1. Why FastAPI for the Backend?
   - High performance, automatic OpenAPI/Swagger documentation generation, strict
     request validation via Pydantic v2 schemas, and seamless asynchronous task support.
2. Why PostgreSQL 17?
   - Enterprise ACID compliance, robust foreign key integrity, powerful recursive
     CTEs for hierarchical team traversal, and native date/time arithmetic in IST.
3. Why React 19 + TypeScript + Vite?
   - Type-safe component development, sub-second hot module reloading, modern hook-based
     state management, and clean modular layout architecture.
4. Why CalibratedClassifierCV for Machine Learning?
   - Standard classifiers output uncalibrated scores that do not reflect true probabilities.
     Sigmoid calibration ensures that a 0.22 delay risk corresponds to an empirical
     22% probability of SLA breach, making the numbers actionable for HR managers.
5. Why Grounded Tool Calling for the Copilot?
   - In HR operations, hallucinations are unacceptable. Grounded tool calling forces
     the model to rely strictly on database records retrieved at runtime, backed by
     a deterministic fallback engine that guarantees zero system downtime.

14.4 EVALUATOR FREQUENTLY ASKED QUESTIONS (FAQ) & MODEL ANSWERS
--------------------------------------------------------------------------------
Q1: How do you prevent the AI Copilot from making up fake employee records?
A: "We enforce strict grounding through function calling. The Copilot is equipped with
10 approved database tools. The system prompt commands the model never to state facts
without retrieving them via tool calls. If no records match, it must state that no
records were found. Furthermore, all responses include verified record citations
linking back to primary database keys."

Q2: How does the system handle role-based data isolation?
A: "Role-based access control is enforced at the database query level in the backend,
not merely hidden on the frontend. When a Reporting Manager accesses an endpoint,
a recursive PostgreSQL CTE identifies all subordinate employee IDs in their reporting
tree. All subsequent queries strictly enforce 'WHERE employee_id IN (:subordinates)'.
Even if a manager crafts a malicious API request for another employee's data, the
backend rejects it with HTTP 403 Forbidden."

Q3: What happens if an external LLM API is down or unconfigured?
A: "HR Flow features a zero-crash deterministic fallback engine. If the LLM API key
is unconfigured or if the remote API times out, 'LLMProvider' automatically intercepts
the call and executes our deterministic grounding engine. It invokes the exact same
SQL tools directly, formats a clean tabular response, and attaches citations, ensuring
uninterrupted operational capability."

Q4: What features does your machine learning model use?
A: "The model relies strictly on 8 operational predictors: days remaining, task category,
task priority, current status, reminder count, owner historical delay rate, owner active
workload, and dependency status. We explicitly blacklist employee and task identifiers
to prevent data leakage and algorithmic bias."

Q5: What is the difference between a Task and a Follow-Up?
A: "A Task represents an internal work unit assigned to an operator (e.g. 'Draft employment
contract'). A Follow-Up represents an active touchpoint awaiting response from an external
stakeholder (e.g. 'Waiting for candidate to return signed offer letter'). Separating
them prevents operators from closing tasks prematurely while waiting for external replies."

Q6: How does task completion synchronize with employee lifecycle records?
A: "Whenever a task is marked 'COMPLETED', the service checks whether it is linked to
a parent lifecycle record (such as Onboarding or Offboarding). If all sibling checklist
tasks for that record are completed, the parent lifecycle record automatically
transitions to 'COMPLETED', updating employee statuses and dashboard metrics atomically."
