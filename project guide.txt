1.1 ARCHITECTURAL PHILOSOPHY & SYSTEM BOUNDARIES
HR Flow is engineered as an enterprise-grade, high-reliability modular monolith designed
for human resources operational workflow intelligence. Rather than adopting an overly
fragmented microservice architecture that introduces network latency, distributed
transaction overhead, and eventual consistency dilemmas, HR Flow consolidates domain
services within a high-throughput, asynchronous FastAPI backend and a responsive,
type-safe React 19 single-page application (SPA).

The system maintains strict architectural boundaries:
1. Presentation Layer (frontend/):
   - React 19 SPA running on Vite 6.
   - Client-side routing with React Router v7.
   - Strict role-gated navigation and layout containment.
   - Zero business rule execution; all decisions and security checks are delegated
     to the backend REST API.
2. API & Controller Layer (backend/app/api/):
   - Fast, automated request deserialization and schema validation via Pydantic v2.
   - Token-based JWT authentication and hierarchical role-based access control (RBAC).
   - Uniform error response handling via custom exception middleware.
3. Domain Service Layer (backend/app/services/):
   - 14 specialized domain services executing discrete business logic (e.g., TaskService,
     LifecycleService, FollowUpService, CopilotService, MLIntelligenceService).
   - Enforces transactional boundaries using SQLAlchemy 2.0 sessions.
4. Data Persistence Layer (backend/app/models/ & database/):
   - Fully normalized PostgreSQL 17 relational database across 23 tables.
   - Managed migrations via Alembic.
   - Strong foreign key relationships, cascade semantics, and composite indexes.
5. Advisory Subsystems (ml/ & backend/app/core/llm_provider.py):
   - Machine Learning: Calibrated Random Forest Classifier predicting task delay risk.
   - GenAI Copilot: Intent-classified, database-grounded tool-calling conversational agent
     backed by a deterministic offline fallback engine.

1.2 COMPONENT COMMUNICATION ARCHITECTURE
The system operates on stateless HTTP/1.1 and HTTP/2 RESTful protocols:
- Client to Server: Axios HTTP client with request/response interceptors that automatically
  attach Bearer JWT tokens from local storage and handle 401 Unauthorized token invalidation.
- Server to Database: SQLAlchemy 2.0 object-relational mapping (ORM) with connection pooling
  via Psycopg 3 over TCP port 5432.
- Server to ML Engine: In-process Python joblib deserialized pipeline (`predictor.py`)
  executing sub-millisecond inference on memory-mapped model weights.
- Server to GenAI Provider: Asynchronous HTTP client (HTTPX) interfacing with OpenAI /
  Google Gemini endpoints, bounded by strict timeout controls and immediate fallback to the
  internal SQL execution engine if external services become unreachable.

2.1 BEGINNER-LEVEL OVERVIEW: WHAT IS HR FLOW?
In simple terms, HR Flow is a mission control center for human resources departments.
In most growing companies, HR tasks—such as sending offer letters, verifying government IDs,
conducting probation check-ins, approving confirmations, and collecting laptop hardware
upon resignation—are managed across spreadsheets, email threads, and post-it notes.
When an HR coordinator forgets to follow up with an IT vendor, a new employee arrives on
Day 1 without a laptop. When a manager forgets to submit a probation review, an employee
is left in limbo for months.

HR Flow solves this by automating the entire lifecycle of an employee from the day they
are hired to the day they leave the organization. It gives every team member—HR Executives,
People Managers, and HR Directors—a single dashboard that lists exactly what needs to be
done today, which tasks are overdue, and what will happen next.

2.2 INTERMEDIATE-LEVEL OVERVIEW: THE ACTION INTELLIGENCE PARADIGM
Traditional Human Resource Information Systems (HRIS) like Workday or BambooHR are "passive
databases of record." They store employee records, addresses, salary bands, and leave balances,
but they do not actively manage daily execution. When a deadline is approaching, a passive
system does nothing until someone runs a manual report.

HR Flow is an "Active Action Intelligence Platform."
- It models tasks as directed operational units with dependencies. Task B (e.g., "Conduct
  Orientation") cannot start until Task A ("Provision IT Assets") is marked complete.
- It tracks two distinct interaction vectors: Tasks (internal work assigned to an operator)
  and Follow-ups (touchpoints waiting for an external response from a candidate or manager).
- It introduces automated multi-tier escalation triggers: if a critical task breaches its
  Service Level Agreement (SLA) by 48 hours, it automatically escalates from the HR Executive
  to the Reporting Manager (Level 1), and then to the HR Director (Level 2).

2.3 ADVANCED / ARCHITECTURAL VALUE PROPOSITION
At the architectural level, HR Flow integrates predictive machine learning and generative AI
directly into relational operational dataflows:
1. Predictive Risk Quantification (Pre-Breach Warning):
   Instead of alerting managers after an SLA has already failed, HR Flow's Machine Learning
   Delay Predictor analyzes 8 operational signals (e.g., operator backlog, remaining days,
   historical delay trends) to output a calibrated probability of delay. This allows
   executives to reallocate workloads days before a breach occurs.
2. Grounded Generative Operations Copilot:
   Rather than relying on generic, hallucination-prone AI chatbots, HR Flow features a
   database-grounded Copilot. The assistant utilizes strict function calling across 12
   custom database tools to inspect live records, summarize bottlenecks, and draft follow-up
   notices, backed by a deterministic SQL execution engine that guarantees 100% availability
   even if external AI services go down.
3. Strict Multi-Level Data Isolation:
   The platform implements recursive hierarchy resolution. An engineering manager logging into
   the system only sees tasks, probation reviews, and analytics for their direct and indirect
   subordinates, enforced at the database SQL layer rather than cosmetic UI masking.

3.2 ARCHITECTURAL SELECTION RATIONALE & TRADE-OFF ANALYSIS

1. Backend: FastAPI vs. Django vs. Node.js (NestJS)
   - Selected: FastAPI
   - Why: Python is the native ecosystem for data science, Scikit-Learn, and LLM integrations.
     FastAPI provides asynchronous execution, native Pydantic validation, automatic OpenAPI
     documentation generation, and execution speeds rivaling Node.js and Go.
   - Alternatives Rejected: Django is overly monolithic and heavyweight for a headless REST
     architecture; NestJS would require running a separate Python sidecar service for the ML
     and data analysis pipelines, adding network complexity.

2. Database: PostgreSQL 17 vs. MySQL vs. MongoDB
   - Selected: PostgreSQL 17
   - Why: HR operations require strict ACID compliance, absolute transactional consistency,
     foreign key constraints, and advanced hierarchical queries. PostgreSQL's Recursive Common
     Table Expressions (CTEs) enable single-query traversal of the entire management reporting
     tree (`WITH RECURSIVE subordinates AS...`).
   - Alternatives Rejected: MongoDB lacks relational integrity constraints, risking orphaned
     tasks and inconsistent employee states; MySQL has weaker recursive query optimization
     and less comprehensive JSON manipulation capabilities.

3. Frontend: React 19 + TypeScript + Vite vs. Next.js (SSR)
   - Selected: Single-Page Application (SPA) with Vite
   - Why: HR Flow is an authenticated internal enterprise portal, not a public search-indexed
     marketing site. An SPA hosted on a static web server eliminates Server-Side Rendering (SSR)
     compute overhead, enables lightning-fast client-side tab navigation, and provides sub-second
     Hot Module Replacement (HMR) during engineering workflows.
   - Alternatives Rejected: Next.js introduces serverless hosting complexity, cold-start
     delays, and hydration mismatches without providing SEO benefits for an authenticated app.

4. Machine Learning: Random Forest with Platt Scaling vs. Deep Learning (PyTorch)
   - Selected: Calibrated Random Forest Classifier (`RandomForestClassifier` + `CalibratedClassifierCV`)
   - Why: Tabular operational data is best handled by tree-based ensembles. Random Forests
     do not suffer from exploding gradients, require minimal memory footprint (< 10 MB RAM),
     support instant serialization via Joblib, and exhibit zero cold-start latency. Sigmoid
     calibration (Platt Scaling) transforms heuristic classification votes into true empirical
     probabilities, ensuring that a 0.25 score genuinely represents a 25% risk of SLA breach.
   - Alternatives Rejected: Deep Neural Networks require massive training datasets, high GPU
     compute resources, and are notoriously prone to uncalibrated overconfidence on tabular data.

5.1 COMPONENT ARCHITECTURE & STATE MANAGEMENT
HR Flow adopts a component-driven, modular frontend architecture. State management is
intentionally lightweight and resilient:
1. Global Authentication State (`AuthContext.tsx`):
   - Stores the active authenticated user object, assigned role code, department, and token.
   - Provides `login()` and `logout()` primitives.
   - Persists JWT tokens to `localStorage` under key `hr_flow_token`, enabling automatic
     session restoration upon browser reload.
2. Route Protection & RBAC Guards (`ProtectedRoute.tsx`):
   - Wraps sensitive routes and inspects `user.role_code`.
   - If an unauthenticated user attempts access, redirects to `/login`.
   - If an unauthorized role attempts access (e.g., a Reporting Manager accessing `/admin`),
     renders a dedicated 403 Forbidden screen.
3. Local Component State & Server Sync:
   - Pages maintain granular local state via standard React `useState` and `useEffect` hooks.
   - Centralized Axios client (`client.ts`) intercepts requests to attach authorization headers
     and intercepts responses to handle expired token redirects (HTTP 401).

5.2 RESPONSIVE LAYOUT & SIDEBAR NAVIGATION SPECIFICATION
The master application shell (`AppLayout.tsx`) manages viewport utilization:
- Top Header: Displays workspace breadcrumbs, dynamic date indicators, user profile pills,
  and quick-action menus.
- Sidebar Navigation:
  * Expanded Width: Exactly 264px (`w-[264px]`), ensuring long enterprise navigation labels
    (e.g., "Follow-ups & Escalations", "Performance Reviews") render completely without
    ellipses or truncation.
  * Collapsed Width: 72px (`w-[72px]`), displaying centered Lucide icons with instant hover
    tooltips.
  * Color Palette: Deep rich brand purple background (`#4318FF` accenting dark navy/slate
    surfaces `#1B2559`), providing high-contrast readability that matches enterprise aesthetic
    standards without overpowering the central workspace.
  * Active Navigation Item: Crisp purple highlight bar with high-contrast text; no distracting
    dots or misaligned indicators.

6.2 FULL REQUEST-RESPONSE EXECUTION TRACE
When a user clicks "Complete Task" on the frontend, the following 10-step lifecycle executes:

1. Ingress & Reverse Proxy:
   - Client issues `PATCH /api/v1/tasks/1387/complete` with header `Authorization: Bearer <jwt>`.
   - FastAPI receives the HTTP connection over Uvicorn ASGI server.
2. CORS & Middleware Processing:
   - FastAPI evaluates the CORS middleware (`CORSMiddleware`). Verifies origin against allowed
     hosts, headers, and HTTP methods.
   - Timing middleware records the start timestamp for request latency metrics.
3. Route Matching & Parameter Extraction:
   - Route matches `/api/v1/tasks/{task_id}/complete` in `backend/app/api/v1/endpoints/tasks.py`.
   - Path parameter `task_id = 1387` is parsed and cast to an integer.
4. Dependency Injection - Database Session:
   - The route requests `db: Session = Depends(get_db)`.
   - The session generator yields a dedicated SQLAlchemy session bound to the connection pool.
5. Dependency Injection - Authentication & RBAC Guard:
   - The route requests `current_user: User = Depends(get_current_user)`.
   - `get_current_user` extracts the JWT from the `Authorization` header, decodes the token
     using `settings.SECRET_KEY` and algorithm `HS256`, and extracts `sub` (email).
   - Queries the database for the active `User` record, pre-loading their assigned `Role`.
   - If token is missing, expired, or user not found, raises `HTTP 401 Unauthorized`.
6. Role-Based Scoping & Permission Check:
   - If the endpoint specifies `require_role(["ADMIN", "HR_MANAGER", "HR_EXECUTIVE"])`,
     `permissions.py` verifies `current_user.role.role_code`.
   - If the user is a `REPORTING_MANAGER`, checks whether the task's associated employee is
     within the manager's reporting line.
7. Service Layer Invocation & Transactional Logic:
   - Router delegates to `TaskService.complete_task(db, task_id=1387, user=current_user)`.
   - TaskService queries the `Task` record by ID. Raises `HTTP 404` if not found.
   - Checks prerequisite dependencies in `task_dependencies`. If any prerequisite task is not
     in status `COMPLETED`, raises `HTTP 400 Bad Request` ("Cannot complete task: Prerequisite
     TSK-01386 is still pending").
8. State Mutation & Cascade Synchronization:
   - Sets `task.status = "COMPLETED"` and `task.completed_at = datetime.now(timezone.utc)`.
   - If the task is linked to an onboarding record, checks if all sibling onboarding tasks are
     now complete. If yes, updates `onboarding_records.overall_status = "COMPLETED"`.
   - If the task is linked to an offboarding record, checks clearance flags (IT, Finance, KT)
     and updates the parent offboarding record accordingly.
   - Closes any active follow-ups or escalations associated with this task.
   - Calls `db.commit()` to finalize the ACID transaction in PostgreSQL.
9. Response Serialization via Pydantic:
   - The mutated ORM model is converted into `TaskResponse` schema via Pydantic's `from_attributes`.
   - Serializes timestamps into ISO 8601 strings and maps nested relationships.
10. Egress & Connection Return:
    - FastAPI returns `HTTP 200 OK` with the JSON response payload.
    - Database session `close()` is invoked, returning the connection to the Psycopg pool.
    - Client updates local React state, reflecting the completed task instantly on the UI.

7.3 ARCHITECTURAL SEPARATION: USER IDENTITY VS. EMPLOYEE RECORD
A crucial design decision in HR Flow is the strict separation between the `users` table and
the `employees` table:
- `employees`: Represents the real-world human being employed by the organization. Contains
  department, joining date, reporting manager, designation, and employment status. An employee
  can exist in the database without having system login access (e.g., historical employees,
  contractors, or employees who have not been provisioned accounts).
- `users`: Represents a system login principal with a secure password hash, JWT credentials,
  and role permissions.
- Linkage: `users.employee_id` holds a foreign key to `employees.id`. This architecture
  guarantees that security authentication concerns (token refresh, password rotation, lockout)
  are completely decoupled from organizational HR management concerns.

8.1 AUTHENTICATION IMPLEMENTATION & TOKEN LIFECYCLE
Authentication in HR Flow follows enterprise OAuth2 Password Bearer specifications:
1. Login Submission:

3. Session Storage & API Interception:
   - Frontend stores the token in browser `localStorage`.
   - The Axios client interceptor attaches `Authorization: Bearer <token>` to every outgoing
     REST call.

8.4 HIERARCHICAL REPORTING SCOPE RESOLUTION ALGORITHM
When a user with role `REPORTING_MANAGER` interacts with any data endpoint, the backend does
not execute simple unfiltered table queries. Instead, `backend/app/core/permissions.py` executes
a Recursive Common Table Expression (CTE) in PostgreSQL to compute the complete transitive
closure of their organizational reporting hierarchy:

```sql
WITH RECURSIVE subordinates AS (
    -- Anchor member: Direct reports whose manager_id matches the manager's employee_id
    SELECT id, manager_id, first_name, last_name
    FROM employees
    WHERE manager_id = :manager_employee_id
    UNION ALL
    -- Recursive member: Subordinates reporting to employees already identified
    SELECT e.id, e.manager_id, e.first_name, e.last_name
    FROM employees e
    INNER JOIN subordinates s ON e.manager_id = s.id
)
SELECT id FROM subordinates;
```
The resulting list of allowed `employee_id` values is injected into the query predicate:
`WHERE tasks.employee_id IN (:subordinate_ids) OR tasks.assigned_to_id = :current_user_id`.
This guarantees mathematically that a Reporting Manager cannot access, manipulate, or query
tasks, appraisals, or documents belonging to other departments.

PART 9: THE 6 EMPLOYEE LIFECYCLE STAGES & OPERATIONAL TRANSITIONS
================================================================================

9.1 STAGE 1: ONBOARDING
- Purpose: Orchestrate all operational activities from the day an employee accepts an offer
  until Day 14 of employment.
- Core Entities: `onboarding_records`, `tasks` (category = 'ONBOARDING').
- Automated Checklists: Provision corporate laptop and email, configure Single Sign-On (SSO),
  conduct Day-1 induction, assign an onboarding buddy, and conduct Day-7 orientation check-in.
- State Progression: `PRE_BOARDING` -> `IN_PROGRESS` -> `COMPLETED`.
- Completion Rule: `onboarding_records.overall_status` automatically transitions to `COMPLETED`
  when all linked onboarding tasks are marked `COMPLETED`.

9.2 STAGE 2: DOCUMENTATION & COMPLIANCE
- Purpose: Ensure mandatory regulatory compliance and identity verification.
- Core Entities: `document_requirements`, `employee_documents`.
- Mandated Documents: Government Identity (PAN Card, Aadhaar), Highest Education Degree
  Certificate, Previous Employment Relieving Letter, Signed Non-Disclosure Agreement (NDA).
- Verification State Machine: `PENDING` -> `UPLOADED` -> `VERIFIED` (or `REJECTED`).
- Verification Rule: Only users with `ADMIN`, `HR_MANAGER`, or `HR_EXECUTIVE` roles can mark
  a document `VERIFIED`.

9.3 STAGE 3: PROBATION MANAGEMENT
- Purpose: Monitor employee performance and cultural alignment during the initial 90 or 180 days.
- Core Entities: `probation_records`, `tasks` (category = 'PROBATION').
- Checkpoint Schedule: 30-Day Checkpoint (Initial alignment), 60-Day Checkpoint (Mid-term
  evaluation), 90-Day Checkpoint (Final probation recommendation).
- Operational States: `UNDER_REVIEW` -> `COMPLETED` (or `EXTENDED`).

9.4 STAGE 4: CONFIRMATION APPROVAL PIPELINE
- Purpose: Formal transition of an employee from probationary status to permanent full-time tenure.
- Core Entities: `confirmation_records`, `employees`.
- The Two-Step Approval Pipeline:
  * Step 1: Reporting Manager Evaluation & Rating:
    The manager evaluates the employee, selects a performance rating (1 to 5), and submits a
    recommendation (`RECOMMEND_CONFIRMATION`, `RECOMMEND_EXTENSION`, or `RECOMMEND_TERMINATION`).
    Status transitions from `PENDING_EVALUATION` to `PENDING_APPROVAL`.
  * Step 2: HR Manager Final Sign-Off:
    The HR Manager reviews the evaluation notes, adds formal HR comments, and approves the
    confirmation.
  * System Mutation: Setting `hr_approval_status = "APPROVED"` automatically mutates
    `employees.employment_status = "CONFIRMED"` and sets `confirmed_date = current_date`.

9.5 STAGE 5: PERFORMANCE REVIEWS
- Purpose: Structured organizational appraisal cycles (quarterly or bi-annual).
- Core Entities: `performance_cycles`, `performance_reviews`.
- Review Workflow:
  * Cycle Initialization: HR Admin launches an active cycle (e.g., "H2 2026 Performance Cycle").
  * Self-Appraisal: Employee logs accomplishments and self-ratings.
  * Manager Appraisal: Reporting Manager provides formal rating and narrative feedback.
  * Final Review: HR calibration and sign-off.

9.6 STAGE 6: OFFBOARDING & CLEARANCES
- Purpose: Graceful separation, asset reclamation, and regulatory compliance upon resignation.
- Core Entities: `offboarding_records`, `tasks` (category = 'OFFBOARDING').
- Mandatory Operational Clearance Triad:
  1. IT Hardware Clearance: Laptop, security tokens, and corporate access revocation.
  2. Finance & Payroll Clearance: Final settlement, expense reimbursements, gratuity calculation.
  3. Knowledge Transfer (KT) Sign-Off: Handover documentation confirmed by Reporting Manager.
- System Mutation: Once all clearances are `COMPLETED`, `offboarding_records.overall_status`
  becomes `COMPLETED`, and `employees.employment_status` is updated to `INACTIVE`.


================================================================================
PART 10: TASK MANAGEMENT, AUTOMATED FOLLOW-UPS & MULTI-TIER ESCALATIONS ENGINE
================================================================================

10.1 TASK INVARIANTS & DEPENDENCY DIRECTED ACYCLIC GRAPH (DAG)
Every operational task in HR Flow adheres to strict invariants:
- Active Statuses: `PENDING`, `IN_PROGRESS`, `BLOCKED`, `DELAYED`.
- Terminal Statuses: `COMPLETED`, `CANCELLED`.
- Dependency Rule: A task cannot transition to `COMPLETED` if any prerequisite task in
  `task_dependencies` has a status other than `COMPLETED`. Attempting to do so triggers an
  `HTTP 400 Bad Request` rejection with a descriptive prerequisite error.
- Automatic Unblocking: When a task is completed, `TaskService` checks all downstream
  dependent tasks. Any dependent task whose prerequisites are now completely satisfied
  automatically transitions from `BLOCKED` to `IN_PROGRESS`.

10.2 FOLLOW-UPS ENGINE: TOUCHPOINTS VS. TASKS
A fundamental innovation in HR Flow is the clean separation of Tasks and Follow-ups:
- A Task represents internal work that the assigned owner is actively executing (e.g.,
  "Draft employment contract").
- A Follow-up represents an external dependency where the operator is waiting for someone
  else to respond (e.g., "Waiting for candidate to submit signed offer letter").
- Why this matters: In standard task trackers, operators leave tasks "In Progress" for weeks
  because they cannot close them while waiting for external replies. In HR Flow, the operator
  schedules a Follow-up with a target date and recipient ("Waiting on: Candidate"). The system
  monitors the follow-up, triggers reminder notifications, and allows recording responses
  without polluting core task cycle times.

10.3 MULTI-TIER SLA BREACH ESCALATIONS ENGINE
HR Flow features a background automated SLA monitoring engine (`run_daily_sla_scheduler`):
- SLA Calculation: A task is breached if `due_date < current_date` and `status` is active.
- Multi-Tier Escalation Thresholds:
  * Level 1 Escalation (Operational Team): Spawned automatically when a task is overdue
    by >= 48 hours. Assigned to the employee's direct Reporting Manager and HR Executive.
  * Level 2 Escalation (Management Review): Triggered if a Level 1 escalation remains
    unacknowledged or unresolved after an additional 48 hours (total 96 hours overdue).
    Assigned to the HR Manager.
  * Level 3 Escalation (Executive Intervention): Spawned immediately if a critical statutory
    milestone (e.g., mandatory compliance documentation or exit clearance) is breached by
    >= 5 days. Assigned directly to the System Administrator / HR Director.
- Resolution Workflow: An escalation can only be resolved by an operator submitting formal
  resolution notes via `/api/v1/escalations/{id}/resolve`. Resolving the escalation clears the
  `is_escalated` flag on the underlying task.

================================================================================
PART 11: MACHINE LEARNING ENGINE: DELAY RISK PREDICTION & CALIBRATION
================================================================================

11.1 PROBLEM FORMULATION & THE ADVANCE WARNING PARADIGM
Standard HR platforms only react after a deadline has failed. HR Flow formulates task
completion as a supervised binary classification and risk scoring problem:
"Given the current operational state of a task at observation time t, what is the probability
that this task will fail to be completed by its designated due_date?"

11.2 MODEL ARCHITECTURE & HYPERPARAMETERS
- Artifact Version: `v2.1.0-phase7a` (located at `ml/artifacts/phase_7a/`)
- Base Algorithm: `RandomForestClassifier` (Scikit-Learn)
  * Number of Estimators (`n_estimators`): 150
  * Maximum Tree Depth (`max_depth`): 6
  * Minimum Samples per Leaf (`min_samples_leaf`): 5
  * Class Weight: None (balanced via probability calibration)
- Calibration Method: Sigmoid (Platt Scaling) via `CalibratedClassifierCV`
  * Why Platt Scaling? Standard random forests output vote fractions that cluster heavily
    around the empirical class mean and do not represent true probabilities. Sigmoid calibration
    fits a logistic transformation over the tree ensemble scores, ensuring that a predicted
    probability of 0.22 corresponds to an exact 22% empirical delay rate.

11.3 THE 8 OPERATIONAL FEATURES (STRICT BIAS & LEAKAGE BLACKLIST)
To ensure algorithmic fairness and prevent target leakage, all employee identifiers (`employee_id`),
personal names, demographic attributes, and task identity keys are strictly blacklisted.
The model ingests only 8 non-biased operational features:

+----+----------------------------+---------+-----------------------------------------------+
| #  | FEATURE NAME               | TYPE    | OPERATIONAL DEFINITION & RANGE                |
+----+----------------------------+---------+-----------------------------------------------+
| 1  | days_remaining             | Integer | Days remaining until target due date (1 to 30)|
| 2  | task_category              | String  | One-hot: ONBOARDING, PROBATION, PERFORMANCE,  |
|    |                            |         | COMPLIANCE, OFFBOARDING                       |

PART 13: OPERATIONAL INSIGHTS, KPIS & ANALYTICS CALCULATION FORMULAS
================================================================================

13.1 EXECUTIVE DASHBOARD METRIC FORMULAS
All dashboard KPIs are calculated via exact SQL aggregations in `dashboard_service.py`:

1. Total Employees (Active Headcount):
   `SELECT COUNT(*) FROM employees WHERE employment_status != 'INACTIVE'`

2. New Joiners This Month:
   `SELECT COUNT(*) FROM employees WHERE date_of_joining >= :start_of_month AND date_of_joining <= :end_of_month`

3. Exits This Month:
   `SELECT COUNT(*) FROM offboarding_records WHERE resignation_date >= :start_of_month AND resignation_date <= :end_of_month`

4. Pending HR Actions:
   `SELECT COUNT(*) FROM tasks WHERE status IN ('PENDING', 'IN_PROGRESS', 'BLOCKED', 'DELAYED')`

13.2 ADVANCED OPERATIONAL METRICS FORMULAS

5. Task SLA Compliance Rate (%):
   Formula: (Total Tasks Completed on or Before Due Date / Total Completed Tasks) * 100
   ```sql
   SELECT ROUND(
       (COUNT(*) FILTER (WHERE completed_at::date <= due_date)::decimal /
        NULLIF(COUNT(*), 0)) * 100, 2
   ) AS sla_compliance_rate
   FROM tasks
   WHERE status = 'COMPLETED';
   ```

6. Average Resolution Time (ART in Hours):
   Measures the average duration from task creation to terminal completion:
   ```sql
   SELECT ROUND(
       AVG(EXTRACT(EPOCH FROM (completed_at - created_at)) / 3600)::numeric, 1
   ) AS avg_resolution_hours
   FROM tasks
   WHERE status = 'COMPLETED';
   ```

7. Department Workload Load Index:
   Quantifies active task distribution normalized by department active headcount:
   Formula: Active Department Tasks / Department Active Headcount
   An index > 4.5 indicates departmental operator strain and elevated delay risk.

8. Operator Bottleneck Score:
   Identifies specific team members who represent operational single points of failure:
   Formula: (Active Backlog Count * 0.4) + (Overdue Task Count * 0.4) + (Historical Delay Rate * 20)

17.1 AUTHENTICATION & CREDENTIAL SECURITY
- Password Hashing: Implements `bcrypt` with automated salting. Passwords are never stored
  in plaintext or reversible encryption formats.
- JSON Web Token (JWT) Security:
  * Signed with HMAC-SHA256 (`HS256`) using a cryptographically secure 256-bit secret key.
  * Token expiration strictly enforced at 480 minutes (8 hours) via standard `exp` claims.
  * Token decoding rejects expired, forged, or unverified signatures with immediate `HTTP 401`.
- Safe Environment Configuration:
  * All production secrets, database credentials, and external API keys are isolated in
    untracked `.env` files. The repository maintains `.env.example` templates with zero real secrets.

17.2 RELATIONAL DATA ISOLATION & INJECTION DEFENSE
- SQL Injection Defense:
  * Zero dynamic string concatenation in SQL queries.
  * 100% of database interactions are authored using SQLAlchemy 2.0 type-safe expressions
    or parameterized SQL statements (`:param_name`), guaranteeing immunity against SQL injection attacks.
- Hierarchical Data Isolation:
  * Role-based data boundaries are enforced at the database level using recursive CTE queries.
  * A Reporting Manager cannot query or manipulate employee records, reviews, or tasks outside
    their organizational hierarchy.

17.3 GENERATIVE AI SAFETY & PROMPT INJECTION DEFENSE
- Read-Only Tool Execution:
  * All 12 Copilot database tools are structurally restricted to read-only queries. The LLM has
    zero capability to drop tables, delete records, reassign tasks, or mutate data.
- System Prompt Hardening:
  * The system prompt explicitly commands the model to refuse attempts to bypass role boundaries,
    reveal internal prompts, or answer non-HR inquiries.
- Hallucination Prevention via Mandatory Citations:
  * The assistant must cite verified primary keys (`TSK-XXXX`, `EMPXXXX`) for every factual statement.
  * If a record is not found in the database, the model is commanded to state that it cannot be found.

17.4 ALGORITHMIC FAIRNESS & ML PRIVACY AUDIT
- Data Minimization:
  * All protected demographic attributes (gender, age, marital status, nationality) and personal
    identifiers (employee name, email, employee code) are strictly excluded from the ML feature set.
- Target Leakage Elimination:
  * Observation snapshots are evaluated strictly on operational state available at prediction
    time (days remaining, current status, owner backlog), preventing post-hoc target leakage.

CATEGORY C: DATABASE, RELATIONAL MODELING & CONCURRENCY (Q21 - Q30)
--------------------------------------------------------------------------------

Q21: Why PostgreSQL 17 instead of a NoSQL database like MongoDB?
A: HR operations require strict ACID transaction guarantees, referential integrity, and cascading
constraints. A task cannot exist without an employee, and an approval cannot exist without a review.
PostgreSQL provides bulletproof relational guarantees and supports recursive CTEs for hierarchical queries.

Q22: How does the database isolate a Reporting Manager's data from other departments?
A: The backend uses a PostgreSQL Recursive Common Table Expression (CTE) to traverse the management
reporting tree from the manager's `employee_id`, collecting all direct and indirect subordinate IDs.
All queries strictly enforce `WHERE employee_id IN (:subordinate_ids)`.

Q23: Why are the `users` and `employees` tables separated in your schema?
A: Decoupling identity from employment records ensures clean separation of concerns. `users` handles
authentication credentials, password hashes, and system roles. `employees` represents the physical
corporate persona (department, designation, manager). This allows employees to exist without system
logins (contractors, alumni) and prevents HR schema changes from impacting authentication security.

Q24: What database connection pool is used and how is it tuned?
A: SQLAlchemy 2.0 connects via the `psycopg` v3 driver with `QueuePool`. It is configured with a
base pool size of 10 connections and a maximum overflow of 20 connections, with a 30-second timeout
and connection pre-ping enabled to discard stale sockets.

Q25: What happens at the database level when a task is marked completed?
A: An atomic transaction is executed: (1) `tasks.status` is set to 'COMPLETED' and `completed_at` is
timestamped, (2) an audit record is inserted into `task_history`, (3) downstream blocked tasks in
`task_dependencies` are evaluated and unblocked, and (4) if linked to an onboarding or offboarding
record, sibling checklist progress is evaluated to potentially complete the parent record.

Q26: What indexes are implemented in your schema to optimize query performance?
A: Composite indexes on `(tasks.employee_id, tasks.status)`, `(tasks.assigned_to_id, tasks.status)`,
`(tasks.due_date, tasks.status)`, `(employees.manager_id)`, and unique indexes on `users.email` and
`employees.employee_code`.

Q27: How are database migrations managed?
A: Database schema versions are managed via Alembic (`alembic/versions/`). Every structural change
is version-controlled and applied programmatically using `alembic upgrade head`.

Q28: How does the platform handle transactional rollbacks?
A: SQLAlchemy session transactions are managed in a Python context manager or try/except block.
If any sub-operation raises an error, `db.rollback()` is invoked immediately, ensuring the database
never remains in a partially mutated or corrupted state.

Q29: How many tables exist in the database and what are the main domains?
A: 23 relational tables across 5 domains: Organization & Identity (4), Workflow & Action Center (6),
Employee Lifecycle (7), Compliance & Documentation (2), and Audit & Intelligence (4).

Q30: How is the synthetic dataset generated and verified?
A: `generate_synthetic_data.py` generates 360 employees, 12 departments, and over 65,000 relational
rows spanning 24 months. `validate_synthetic_data.py` executes a 10-point mathematical integrity test
verifying foreign keys, timeline chronology, and status invariants before data loading.

Q32: Why is probability calibration (Platt Scaling) necessary?
A: Standard classification algorithms output heuristic voting scores that do not reflect empirical
probabilities. Platt Scaling applies a logistic transformation over the tree ensemble scores, ensuring
that a predicted risk score of 0.20 corresponds to an actual 20% empirical rate of task delay.

A: Low Risk (< 0.12, green indicator): normal progression. Medium Risk (0.12 to 0.22, yellow indicator):

   - Current State: The ML engine functions in advisory "shadow mode"—it flags risks and suggests
     interventions to human operators, but does not autonomously reassign tasks or mutate deadlines.

5. Simulated Outbound Communication:
   - Current State: The platform drafts professional follow-up reminders and logs notifications
     in the database, but does not connect to an external SMTP server or Twilio SMS gateway for
     physical email/SMS transmission.

21.2 PRIORITIZED ENHANCEMENT ROADMAP
